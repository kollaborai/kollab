  the one I introduced (data loss, fixed)
  My keyring guard made APIKeyManager.store_key() return silently when disabled.
  Two callers treat "no exception" as "the key is safely stored" and then
  delete their plaintext copy — migration.py::_try_os_keyring (which pops

  was gone from both places.
  - fix: store_key now raises KeyringDisabledError. Both callers already catch
  and fall through, so the tier chain works with no caller changes.
  - proof: reran the auditor's scenario with an in-memory fake keyring —
  _try_os_keyring → False, keyring empty, and the migrated profile keeps
  api_key: sk-secret. Pinned with two tests.
  - blast radius was zero today (ProfileMigrator isn't wired into the live
  startup path) but KOLLAB_NO_KEYRING is now documented for headless runs, so it
  was one wiring change from eating a real key.

  nits fixed (3)
  - the harness set the guard by typing export KOLLAB_NO_KEYRING=1 into the pane
  — bash/zsh syntax that a fish/csh default shell rejects, silently booting the
  app unguarded, i.e. the exact dialog bug back. Now prefixed with env (an
  external binary, shell-agnostic). I tried tmux's -e first and verified it does
  not reach the initial pane, so env it is; confirmed delivery with a probe.
  - the spec's \d+ models? assertion would pass on "1 model" — the original bug.

  - llm_service raised AttributeError when event_bus is literally None, after
