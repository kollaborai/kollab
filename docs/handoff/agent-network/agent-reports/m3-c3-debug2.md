# c3-members debug 2: link refresh livelock between members (partial fix, not committed)

- Failure named (B log 08:52 on, A log the same): `PeerRouteError: peer link proposal does not match the live session` every ~15 s, plus `has an invalid lifetime` and `revision rollback`, ending in `peer forwarding ingress session is stale`. It hits A<->B too, not only B<->C. B's directory call to C then fails with `RelayError: peer route delivery failed` (the link is judged live on B, stale on C).
- Reproduced without live hosts: the `net` harness in `tests/unit/test_mesh_fallback.py`, `refresh(b, c)` in both directions concurrently, `time.time` advanced 15 s per round. Errors start at +60 s and never clear by +450 s (`link_between` is None on both, each side's `link_session_id` differs).
- Root causes (all in `plugins/hub/peer_transport.py`, `secure_conversation.py`):
  1. `_make_link_signature` re-proposes an unchanged link with its old `issued_at`; `_accept_link_signature` demands `issued_at >= now - 60`, so every refresh past 60 s is rejected ("invalid lifetime") and the rejection drops the sessions.
  2. A renewal past half life on the same session proposes `next_revision`; the responder expects the current revision when the session is unchanged ("does not match").
  3. `link_session_id` = min over both directions' sessions. The initiator drops its half after a failed request; the responder's half stays (300 s idle). Each node then sees different sessions, the ids disagree, and every rejected proposal leaves one more orphan half, so it never heals.
  4. Both nodes propose at the same tick, each naming its own session and revision, so they end up with two different links (equivocation/rollback).
- Fix tried (uncommitted in this worktree, saved as `m3-c3-debug2-wip.patch`, 1 branch of the diff on `plugins/hub/*`): proposal names the outbound session, responder names the carrying session (contextvar), links checked by membership in the live session set, accept `next_revision` and a byte-identical restated link past 60 s, and only the lower peer id proposes.
- Result: B and C now hold the SAME link every round and the first 135 s are clean (was: broken at 60 s). Still failing after the first renewal (+150 s): `revision rollback` and `does not match` in exchanges with the third member A, whose link store runs ahead of the proposer's when a proposal is accepted but its response fails validation; also 4 existing tests fail with the patch: `test_peer_transport.py::test_three_peer_carrier_delivers_secure_directory_and_replay_once`, `::test_a_refused_direct_secure_record_still_takes_the_routed_path`, `test_mesh_network.py::test_a_link_proposal_is_made_only_after_the_outbound_session_is_open` (+1 more). They likely assume both sides propose or read `link_session_id`.
