# B to C secure sessions: stale peer link refuses the handshake (fixed, not yet proven live)

- Hypothesis (direct-first deadlock, locator missing on one side): refuted. B and C on the relay, both with endpoints, approved by A's vouch only, with no, one-sided or both locators: a `directory` request in both directions plus a second round over the link all succeed before any change. Locators come from UDP discovery, not sessions, and `_DIRECT_FAILED` already falls back to the relay.
- Root cause: `PeerMeshRuntime.request` (`plugins/hub/peer_transport.py`) sent `secure_identity` down the signed-link mesh path whenever a link to a relay-roster peer existed and a locator did, without checking the link's session id against a live TLS session (`secure_packet` had that check).
- Once either side's TLS session lapses or is dropped after a failed request, the link outlives it. Every handshake meant to replace the session is then wrapped in a `peer_forward` frame that the responder refuses with `PeerRouteError: peer forwarding ingress session is stale` (`_route_material`), on the direct endpoint and again on the relay fallback. Deadlock, retried every ~15 s. Needs a locator on the caller, so A (no endpoint) was never hit.
- Reproduced before the fix with the live log signature (`authenticated peer forwarding failed` on the responder, `RelayError: peer application request failed` on the caller): `test_a_link_whose_sessions_are_gone_does_not_block_the_next_handshake` in `tests/unit/test_mesh_fallback.py`.
- Fix (92f99cf, refs #121): the mesh path is taken only when a link names the live TLS session, for both methods; otherwise the native relay path.
- Logging: `failure_text` in `relay_state.py` logs the class, and the message only for RelayError, PeerRouteError and SecureSessionError. Wired into `relay_client._dispatch_request`, `secure_conversation.handle_packet`, the direct endpoint in `messenger.py`, and `peer_transport.handle_forward` (it hid the real PeerRouteError). One test each.
